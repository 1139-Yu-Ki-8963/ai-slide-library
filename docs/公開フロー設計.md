# スライド公開フロー設計

`adding-catalog-slides` が担う登録・公開フローの設計。
2026-07-28 の新デザイン移行で顕在化した欠陥を是正した形を定める。

## 1. 現行フローで起きたこと

いずれもこのリポジトリでの実測。

| 事象 | 結果 |
|---|---|
| 承認範囲を超えた46スライドの削除が実行され、公開まで到達した | 公開サイトから46枚が1時間以上消えた |
| ユーザーが内容を承認した後にAIレビューが6件の修正を要求した | 規約の緩和と再判定を6周した |
| 低優先度の提案1件で集約が blocked になりコミットが止まった | 文字サイズ22pxの指摘で公開が停止した |
| 検査ジョブを廃止したら配信ジョブも止まりかけた | GitHub Pages が workflow 配信のため、検査を消すと公開経路が消える |
| 正本と公開資産の同期順序を誤り、バイト一致検査で配信が止まった | 46枚の復旧が検査失敗で2回ブロックされた |
| 49枚一括の実描画検査で4枚目のチェッカーが異常終了した | 個別実行では49枚すべて通るのに、一括では全体が止まった |

## 2. 設計原則

### 原則1: 止める権限を3種類に分ける

| 権限 | 担当 | 止めるか |
|---|---|---|
| 機械検証 | 構造契約・表示破綻・公開安全の自動検査 | 常に止める |
| ユーザー承認 | 人の判断 | 最上位。承認が最終決定 |
| AIレビュー | 図表・情報設計・実務性の所見 | **止めない。記録して人に渡す** |

AIレビューの役割は判断材料の提供であり、拒否権ではない。
所見はユーザー提示のときに添え、採否は人が決める。

### 原則2: 承認は「対象 × 操作」で取る

削除は追加・更新と別の承認とする。
削除を実行する前に、対象を全件列挙して承認を取る。
承認された件数と実際に削除する件数が一致しない場合は実行しない。

| 操作 | 承認の取り方 |
|---|---|
| 追加 | 対象キーと枚数を提示 |
| 更新 | 対象キーと変更内容を提示 |
| 削除 | **対象キーを全件列挙し、件数を明示して個別承認** |

「既存のものを置き換える」という表現は、更新と削除のどちらにも読める。
読み違えが起きうる表現を受けた場合、どちらかを確定してから進める。

### 原則3: 規約は実物から導く

承認された実物から規約を抽出して固定し、以後の新規スライドをそれで検査する。
実物より先に規約を書かない。

既存の実物と規約が食い違った場合、実物を正とする。
規約側を実物に合わせ、変更の理由と捨てた案を記録する。

### 原則4: 検査と配信を分離する

ワークフローを2本に分ける。

| ファイル | トリガ | 内容 |
|---|---|---|
| `verify.yml` | pull_request | 機械検証。失敗すればPRのマージを止める |
| `deploy.yml` | main への push | 配信のみ。検査ジョブに依存しない |

検査を止めても配信は生きる構成にする。
GitHub Pages は `build_type: workflow` で配信されるため、配信ジョブを含むワークフローの削除は公開の停止を意味する。

### 原則5: 正本の同期は単一の操作にまとめる

グローバルスキルの正本 `references/shared-slide-shell.css` と公開資産 `assets/shared-slide-shell.css` のバイト一致は、同期忘れの検出が目的である。
検査は「同期スクリプトを実行したら差分が出るか」で判定し、両リポジトリの更新順序に依存させない。

正本を変更したら、同じ作業単位で公開資産へ同期し、両方をコミットする。

### 原則6: 検査の失敗単位をスライド単位にする

1枚の失敗が全体を止めない構成にする。
実描画検査は対象ごとに独立したプロセスで実行し、1枚の異常終了で母集団全体を落とさない。
失敗した枚のキーを報告し、その枚だけを差し戻す。

### 原則7: 検証の範囲を変更規模に比例させる

全件母集団への検証を既定にしない。
変更の種類ごとに、実行する検証を次の表で決める。

| 変更の種類 | 機械検証 | AIレビュー | 敵対的検証 |
| --- | --- | --- | --- |
| 台帳・語彙のみ（HTML不変） | カタログ整合のみ | なし | なし |
| 1〜3枚の更新 | 対象枚のみ | 対象枚のみ | PR差分のみ |
| 新規追加・型追加 | 対象枚＋全件の契約検査 | 対象枚のみ | 必須 |
| 共有シェル・共有JavaScriptの変更 | 全件 | 代表3枚 | 必須 |

共有シェルの変更だけが全件検証を要する。
全スライドが同じCSSを直接参照するため、1箇所の変更が全枚に及ぶためである。

台帳・語彙のみの変更でAIレビューと敵対的検証を実行しない。
HTMLが変わらない変更に、図表・情報設計のレビューを適用する意味がない。

## 3. フロー

```
A 対象確定と承認
   A-1 変更を追加・更新・削除に分類する
   A-2 削除がある場合、対象キーを全件列挙して承認を取る
   A-3 追加・更新の対象を確定する
        ↓
B 生成・更新
   generating-explanation-html-slides が担当する
        ↓
C 機械検証（止める）
   C-1 構造契約（共通シェル・論理ページ・ヘッダー契約）
   C-2 表示破綻(実描画・はみ出し・サムネイル)
   C-3 公開安全(個人名・顧客名・絶対パス・端末固有情報)
   スライド単位で判定し、失敗した枚だけ B へ差し戻す
        ↓
D AIレビュー（止めない）
   D-1 単一スライドの図表・情報設計
   D-2 デッキ全体のアートディレクション
   D-3 情報過多・分割要否
   D-4 実務性・非テンプレ感
   所見を検査記録へ保存する。公開は止めない
        ↓
E ユーザー提示と承認（最終判断）
   E-1 実物HTMLをローカルサーバーで提示する
   E-2 D の所見を添える
   E-3 承認を取る
        ↓
F 登録・生成
   F-1 蓄積簿・主題一覧を更新する
   F-2 サムネイル・カタログを再生成する
        ↓
G コミット・公開
   G-1 コミットする
   G-2 push する
   G-3 配信の完了と公開物を確認する
```

承認（E）の後に実行するのは F と G だけである。
E の後に D を再実行しない。C は F でカタログが変わるため、G の直前に1回だけ再実行する。

## 4. 停止条件

| 段階 | 止める条件 |
|---|---|
| C | 構造契約・表示破綻・公開安全のいずれかが fail |
| D | 止めない |
| E | ユーザーが承認しない |
| G | F が生成した成果物の整合が fail（カタログ・サムネイル・台帳の対応） |

承認（E）の後にスライド本体を再検査しない。
G で検証するのは F が生成したもの、すなわちカタログと台帳とスライドの対応、サムネイルの寸法だけである。
承認済みの内容が G で覆ることはない。

集約判定の blocker は `critical` と `fail` に限定する。
`hold` と `suggestion` は記録に残すが止めない。

## 6. 検証方法

| 原則 | 検証 |
|---|---|
| 原則1 | AIレビューで `hold` を出したスライドが、承認後に公開まで到達すること |
| 原則2 | 削除対象の件数が承認件数と一致しない場合に実行が止まること |
| 原則3 | 実物と規約が食い違ったとき、規約側を直す手順が文書に存在すること |
| 原則4 | `verify.yml` を削除しても `deploy.yml` による配信が動作すること |
| 原則5 | 正本のみを変更した状態でバイト一致検査が同期を促し、配信を止めないこと |
| 原則6 | 1枚を意図的に壊したとき、その1枚だけが fail になり他が通ること |
| 原則7 | 台帳1行の変更でAIレビューと敵対的検証が実行されないこと |
