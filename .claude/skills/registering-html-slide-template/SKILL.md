# HTMLスライド型登録

既存スライド群との共通シェルを調査し、新しい型を再利用可能な登録資産として追加する。実際の1枚の生成は `generating-explanation-html-slides` に委譲し、このスキルは型の定義・登録・検証・公開までを統括する。

## 使用タイミング

- 新しいレイアウト型を既存ライブラリへ追加するとき
- 参考画像から再利用可能なスライド型を登録するとき
- 既存型では表現できない診断・比較・工程図などを型として残すとき

次の場合は既存の `generating-explanation-html-slides` を使う。

- 既存型のルール内でスライドを1枚だけ作る
- カタログや蓄積簿の型定義を変更しない

## 基本ワークフロー

### Phase 1: 仕様と対象範囲を確定

完了条件: 参考画像、読み手、結論、制約、型名候補、対象リポジトリが記録されている。

1. 参考画像とユーザー固有の背景色・サイズ・余白・ヘッダー・フッター規約を読む。
2. 既存の蓄積簿、カタログ生成スクリプト、代表スライドを確認する。
3. 「既存型の派生」か「新規型」かを判定する。判断できない場合は勝手に登録せず確認する。
4. 型名は意味語で確定し、既存キー・型名との重複を確認する。

### Phase 2: 共通シェルを調査して固定

完了条件: 全スライド走査の結果と、新型が守る共通シェル契約が表になっている。

1. `slides/*/解説スライド.html` を全件走査する。
2. 次の共通契約を機械的に比較する。
   - `.slide-viewport`、`.slide`、`.slide-header`、`.slide-title`
   - 1280×720、縮小式、横スクロールなし
   - `footer.slide-meta`
   - ページ背景、白いスライド面、文字色、罫線、角丸、影
3. リダイレクト用HTMLと実表示HTMLを分ける。
4. 例外スライドは内容を壊さず、共通シェルとの差分を修正方針に記録する。

### Phase 3: 新型を生成

完了条件: 共通シェルを満たすサンプルHTMLと、内容が判別できるサムネイルが作成されている。

1. `generating-explanation-html-slides` の型選択・構造設計・レビュー手順を再利用する。
2. ヘッダー、タイトル、フッター、背景、サイズ、縮小処理はPhase 2の契約を優先する。
3. 型固有の図表や中央レイアウトだけを新規実装する。
4. サンプル文言・数値は実データと誤認されないよう、必要に応じて「例」「サンプル」と明記する。
5. サムネイルは公開成果物として `slides/<key>/サムネイル.png` に置く。検証用スクリーンショットは `~/agent-home/tools/MCP/playwright/` に絶対パスで保存する。

### Phase 4: カタログへ登録

完了条件: 蓄積簿・型検証・一覧データが新型を認識し、生成検査が成功している。

1. 蓄積簿に型名、説明対象、提示課題、タグ、登録日を追加する。
2. カタログ生成スクリプトの許可型一覧へ新型を追加する。
3. `node scripts/build-catalog.mjs` を実行する。
4. 生成された一覧に新型、HTMLリンク、サムネイルリンクがあることを確認する。
5. スライドをコミットした後に、カタログをもう一度生成する。`updated` は実際のスライドコミット日を使うため、先に生成すると更新順が古いままになる。

### Phase 5: レビューと実機検証

完了条件: 固定レビュー、HTMLレビュー、表示検証、内容検証がすべて合格している。

1. `managing-review-sets` のHTML成果物プロファイルを実行する。
2. 既存型との共通シェル差分を再走査する。
3. Playwright MCPが利用可能なら、ページを開き1280×720と375×667で検証する。利用できない場合は利用可能なPlaywright手段で代替し、保存先規約を守る。
4. 次を確認する。
   - デスクトップで内容が切れない
   - モバイルで横スクロールしない
   - ヘッダー・タイトル・フッターが共通契約を満たす
   - サムネイルだけで内容と型が判別できる
   - 外部画像・外部フォントが必須ではない
5. 指摘があれば一括修正し、全レビューを再実行する。

### Phase 6: 公開反映

完了条件: 公開リポジトリと公開URLの一覧・HTML・サムネイルが一致している。

1. 変更範囲を確認し、無関係な変更を含めずにコミットする。
2. `main`へpushする。
3. 公開一覧、個別HTML、サムネイルをHTTPで確認する。
4. 公開一覧の更新日と並び順を確認する。同日更新のタイブレークも記録する。

| 用途 | 手段 |

| カタログ生成 | `node scripts/build-catalog.mjs` |

## 重要な注意事項

- 新型登録と単発スライド作成を混同しない。
- 参考画像は構造・余白・配色・情報密度の参照に限定し、画像内の固有文言・数値・サンプル内容をそのまま複製しない。タイトル・本文・数値は対象リポジトリのテーマへ置き換える。
- 共通クラス名だけで「統一済み」と判断せず、色・寸法・縮小式・フッター構造も比較する。
- ユーザー固有の指摘（背景はページ外を薄青、スライド面は白、1280×720固定、共通ヘッダー・タイトル・フッター、中央要素の余白、角丸、モバイル縮小、サムネイル全体表示、カタログの更新順、コミット・push・公開確認）を実装前チェックリストへ転記し、1項目ずつ検証する。
- レビュー時は「ヘッダー・フッターの有無」「タイトルの階層」「内容のサンプル流用」「中央レイアウトの詰まり・欠け」「一覧サムネイルと実物の一致」を独立した合否項目として判定する。
- このリポジトリの正本は `.claude/skills/` に置く。`.codex/skills/` は同じ2つのリポジトリ内スキルへの相対シンボリックリンクだけを置き、`.claude/skills/`へ無関係な共通スキルを追加しない。
- リダイレクト用HTMLを実表示スライドとして数えない。
- 公開用サムネイルはカタログ参照先なのでリポジトリ内に置く。検証用スクショとは保存先を分ける。
- スライドをコミットする前に一覧を生成しない。更新順のメタデータが古くなる。
- push後はローカル検査だけで完了にせず、公開URLを再確認する。

## 予想を裏切る挙動

HTMLとサムネイルがローカルで存在しても、カタログ生成前・Pagesデプロイ前は公開一覧に現れない。更新日もスライドのGitコミット後にカタログを再生成しないと古いままになる。
