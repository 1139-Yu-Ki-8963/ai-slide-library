# カタログスライド追加（adding-catalog-slides）

ai-slide-library 専用の登録オーケストレーター。スライドの生成・品質検査は共通スキル generating-explanation-html-slides に委譲し、本スキルはこのリポジトリ固有の登録工程（タグ付与・蓄積簿追記・カタログ再生成・公開）を統制する。

## 使用タイミング

- このリポジトリでスライドを新規追加し、公開カタログへ反映する時
- 既存スライドの内容・タイトル・タグを更新し、サムネイル・蓄積簿・カタログへ追従させる時

## 基本ワークフロー

### Phase 1: 作業ブランチ準備

1. `Skill("parallel-dev-worktree")` で feature ブランチの worktree を作成する（メインツリーの直接編集は hook で block される）
2. 以降の作業はすべて worktree 内で行う

完了条件: worktree 内で `git status` がクリーンであること

### Phase 2: スライド生成（共通スキルへ委譲）

1. `Skill("generating-explanation-html-slides")` を起動し、出力先ディレクトリとして worktree 内の `slides/` を指定する（保存先は `slides/<スライドキー>/解説スライド.html` と同フォルダの `検査記録.md`）
2. 共通スキル側の蓄積簿登録工程（旧5列形式）は実行しない。蓄積簿の列構成は本リポジトリの `docs/スライド蓄積簿.md` の記入規則が正であり、本スキルの Phase 3 が代替する

#### 既存スライドの更新の場合

1. 対象の `slides/<スライドキー>/解説スライド.html` を直接編集するか、`Skill("generating-explanation-html-slides")` で再生成する
2. 更新前のスライドのデザインシステム（CSS 変数・レイアウト構造・コンポーネント）を踏襲すること。元の HTML を Read してから着手する

#### 改善版の情報保持・指摘反映ゲート

改善版は「見た目を作り直す作業」ではなく、既存内容を保持した上でユーザー指摘だけを反映する差分作業とする。元スライドにある情報を、明示承認なしに削除・統合・一般化してはならない。

1. Before から情報台帳を作る。タイトル、サブタイトル、見出し、列名、カード名、モデル名（例: Opus / Sonnet / Haiku）、使用例、数値、注記、フッター、凡例、主張を列挙する。画像が正本の場合は目視/OCRで同じ台帳を作る
2. ユーザー指摘を要求台帳に変換する。各行は「指摘原文 / 対象箇所 / 必須変更 / 保持する既存情報 / 合格文言」で記録し、指摘の言い換えで要件を弱めない
3. After の差分を3分類する: `必須変更`、`保持`、`追加`。`保持`の項目がAfterから消えた場合は即FAILとし、ユーザー承認なしに次工程へ進まない
4. 実装後に、Before/Afterのテキスト・属性・画像内要素を突合する。機械検索（`rg`等）で固有語・モデル名・数値を確認し、画像由来の要素は目視で確認する。タイトル・見出し・注記は表記揺れ・助詞・誤字まで原文と照合する
5. 構造レビューと内容保持レビューを分離して並行実施する。内容保持レビューは「欠落0件」、指摘反映レビューは「要求台帳の必須変更全件PASS」を完了条件とする
6. レビューHTMLには、Before/After画像だけでなく「適用規約」「ユーザー指摘」「保持した情報」「変更した情報」「未承認のため変更していない情報」を同じHTML内に表示する。読み手が別資料へ移動しなくても採否判断できる状態にする
7. レビューHTMLは `templates/before-after-review.html` を複製して作る。要求台帳は `templates/requirements-ledger.md`、携帯URLの配信・検証は `templates/mobile-review-checklist.md` を使い、手順を毎回再現する
8. サンプル型の構造を変更する判断をした場合は、変更理由・規約違反箇所・保持した関係・新しい型名候補を要求台帳に記録する。これは内容変更ではなく型変更として扱い、ユーザー承認前に正式テンプレート登録や公開を行わない

完了条件: Beforeの情報台帳に対する欠落0件、要求台帳の必須変更全件PASS、表記照合PASS、レビューHTML内の根拠表示PASS。いずれかが未確認ならユーザー提示を禁止する

#### 必須語・指摘・校正の機械検証

1. Before情報台帳と要求台帳から必須語チェックリストを作る。モデル名（例: Opus / Sonnet / Haiku）、数値、固有見出し、ユーザーが指定した表記を、存在・出現数・対応説明まで確認する
2. Afterで必須語が1件でも欠落、別語へ置換、対応説明が消失した場合はFAILとする。見た目が改善されても情報欠落として提示禁止にする
3. Before/After、レビューHTML、検査記録に対して textlint またはプロジェクトの辞書検査を実行し、タイトル・見出し・注記・表セルの誤字と表記揺れを確認する。検査不能時は「未検証」と記録し、PASS扱いにしない
4. ユーザー指摘を会話、コメント、添付画像の注記から全件収集し、要求台帳の件数と突合する。未分類・未反映・判断待ちが1件でもあればFAILとする
5. 最終レビューでは要求台帳を1行ずつ `PASS / 保留 / 対象外（理由付き）` で記録する。保留が残る場合はユーザー提示せず、確認を求める

#### 必須テストシナリオ

- **必須語欠落検知**: AfterからHaikuまたはその対応説明を削除し、必須語チェックがFAILになること
- **誤字検知**: タイトルまたは見出しの一文字を誤記し、textlintまたは表記照合がFAILになること
- **指摘取りこぼし検知**: 要求台帳の1行を未反映にし、台帳突合がFAILになること

完了条件: 上記3シナリオすべてで、意図的な欠陥をFAILとして検出できること

#### 既存スライドの修正承認ゲート（公開・正式反映とは分離）

既存スライドの改善依頼では、正式ファイルを変更する前に必ず以下を行う。これはレビュー提示の手順であり、公開許可を意味しない。

1. 現在の公開版を Before として保存し、改善案をローカル一時成果物として作成する。既存の `slides/`、`index.html`、蓄積簿、主題一覧はこの段階で変更しない
2. Before（現在版）を1枚目、After（改善提案）を2枚目とする比較用HTMLを1つ作成する。比較用HTMLには「公開禁止・ユーザーレビュー専用」と明記し、公開対象ディレクトリへ置かない
3. 比較用HTMLをユーザーへ提示し、改善対象・改善理由・変更しない対象を説明する
4. ユーザーが改善内容を承認するまで、正式スライド・サムネイル・検査記録・蓄積簿・主題一覧・カタログを変更しない
5. 承認後に限り正式ファイルへ反映し、Phase 3〜5を実行する。改善承認は公開承認ではないため、Phase 6へ自動遷移しない

ゲート完了条件: Before/After比較HTMLを提示済みで、正式反映・公開はユーザーの明示承認待ちになっていること

#### モバイル向けURL提示（公開禁止）

ユーザーがURLでの確認を求めた場合は、比較HTMLを1枚に全件詰め込まず、対象スライドごとに独立したレビューHTMLを1つずつ作る。6件なら6件のURLを提示し、各URLは「現在版1枚 → 改善提案1枚」だけを表示する。

1. 比較HTMLと画像はリポジトリの `slides/`、`index.html`、公開サイトの配信対象へ置かず、ローカルのレビュー用ディレクトリへ保存する
2. モバイル確認用の配信は、レビュー成果物だけをドキュメントルートにしたLAN限定サーバーを使う。リポジトリ全体をドキュメントルートにしない。公開サイト、GitHub Pages、外部ホスティング、トンネルサービスは使わない。待受アドレスはユーザー指定のプライベートIPに限定し、`0.0.0.0`で公開しない
3. サーバーを起動しただけでは完了としない。URL提示直前に、同じプライベートIP・ポートへの接続を `curl` で実行し、HTML本体がHTTP 200で取得できることを確認する。サーバープロセスが停止・切断している場合はURLを提示せず、再起動して再検証する
4. URL提示前に、対象件数分の各URLがHTTP 200であること、各HTMLが画像2枚だけを読み込むこと、画像リクエストもHTTP 200であること、390px幅で横溢れしないことを確認する
5. URLはユーザーへのチャット提示に限り使用する。プライベートIP（例: `192.168.x.x`）をHTML、リポジトリ、カタログ、コミット、公開ログへ書き込まない。グローバルIPや公開URLへ置き換えない
6. 6件のURLは同一の集合HTMLへのアンカーリンクではなく、6つの独立HTMLのURLを提示する。1つのURLに全件を縮小表示してはならない
7. 実機のモバイル端末を操作できない場合は「Mac上のモバイル幅エミュレーションとLAN側HTTP確認」と明記し、モバイル実機で確認済みとは報告しない

完了条件: 対象件数と同数の独立URLを提示し、提示直前の待受確認、各URLのHTML・画像HTTP確認、画像2枚確認、モバイル幅検証が完了していること。いずれかが失敗した場合はURLを提示せず、失敗内容と再起動・再検証結果を先に報告する。公開・commit・pushは行わない

Phase 2（正式反映後）の完了条件: 観点レビュー表の全行 PASS のスライドと検査記録が `slides/<スライドキー>/` に保存されていること

### Phase 3: タグ付与と蓄積簿追記

1. `docs/スライド蓄積簿.md` の「タグ語彙一覧」を Read し、対象ツール・仕組み・テーマを既存語から選ぶ
2. 既存語で表せない概念がある場合のみ、表記統一基準（技術要素は英語の正式名称・テーマは日本語・1語=1概念）に従って先に語彙一覧へ追加する
3. 「スライド一覧」表へ12列形式（スライドキー / 説明対象 / 提示する課題の例 / 対象ツール / 仕組み / テーマ / 導入段階 / 取り込み実体 / パック / 導入プロンプト / テンプレート / 登録日）で1行追記する。複数値は「、」区切り、該当なしの軸は「—」。テンプレート列は生成時に使用したテンプレートファイルに対応する種別名（図解型 = slide-template.html / 課題分析テーブル型 = argument-table-template.html / 現状理想対比テーブル型 = gap-analysis-table-template.html）を記入する
4. `docs/スライド主題一覧.md` に、スライドキーと「この1枚で何を理解してほしいか」を一文で追記する。主題はタイトルや説明対象の言い換えではなく、スライドの結論・判断・行動を句点付きで記述する。既存スライドの主題を変更する場合は該当行を更新し、新規行を重複追加しない

#### 既存スライドの更新の場合

1. 蓄積簿の該当行を更新する（新規行を追加しない）
2. スライドのタイトルを変更した場合は「説明対象」列がスライド内容と整合していることを確認する
3. タグを変更した場合は語彙一覧との照合を再実施する

完了条件: 追記行の全タグが語彙一覧に存在すること

### Phase 4: サムネイル生成・カタログ再生成と検証

1. サムネイルを生成する: プロジェクトルートに playwright を一時リンク（`ln -sfn <playwright-node_modules-path> node_modules`）し、`node scripts/build-thumbs.mjs` を実行する。完了後にリンクを外す（`rm -f node_modules`）。対象スライドの `slides/<スライドキー>/サムネイル.png` が生成（新規）または更新（既存）されたことを確認する
2. `node scripts/build-catalog.mjs` を実行する
3. 成功出力のスライド枚数が期待枚数と一致すること、index.html に対象スライドキーと `purpose` が埋め込まれていること（grep）を確認する。更新の場合はタイトル・タグ・主題の変更が反映されていることも grep で確認する
4. 語彙一覧に無いタグでビルドが停止した場合は Phase 3 に戻り、語彙一覧かタグを修正する。蓄積簿未登録フォルダの検出で停止した場合も Phase 3 に戻り、蓄積簿へ追記する
5. ローカルプレビュー: `index.html` をブラウザで開き、対象スライドのサムネイルが更新後の内容を反映していることを目視確認する
6. 検索検証: 検索ボックスにスライドタイトルの主要語を入力し、対象スライドが検索結果に表示されることを確認する
7. **更新順の事前確認**: 新規・更新スライドは、この段階では未コミットのため `updatedAt` が確定していない。公開前の先頭表示確認は Phase 6 のコミット後再生成を完了してから行い、ここで完了扱いにしない

完了条件: サムネイルが生成され、カタログ再生成が成功し、枚数一致と対象キーの埋め込みが確認され、ローカルプレビューで対象スライドが検索・表示できること
### Phase 5: 公開可否レビュー

公開リポジトリにユーザー固有情報が混入していないことを 2 段階で検査する。reviewing-public-readiness 単独ではプロジェクト固有名（任意文字列）を検出できないため、Step 5-1 のスライド固有チェックが必須の補完となる。

#### Step 5-1: スライド固有の公開安全チェック

新規・変更されたスライド HTML / 検査記録 / 蓄積簿を対象に、ユーザー環境の固有名が混入していないことを確認する。reviewing-public-readiness の検出パターンでは捕捉できない漏洩クラス（プロジェクト名・アカウント名・セッション名・ブランチ名等の任意固有文字列）を補完する。

1. スライド内の例示値（ターミナルモックアップ・コード例等）を列挙する
2. 各例示値がユーザーの実環境から取った固有名でないことを確認する
3. 固有名を発見した場合は汎用的な例示値（my-project / my-account 等）に差し替える
4. 検査記録.md・蓄積簿にも同様の固有名がないことを確認する

#### Step 5-2: reviewing-public-readiness による汎用走査

1. worktree 内で `git add -A` を実行し、新規ファイルをインデックスに載せる（git 系走査が未追跡ファイルを素通りする問題の回避）
2. `Skill("reviewing-public-readiness")` を worktree のリポジトリルートで実行する
3. CRITICAL が 1 件でもあれば該当箇所の詳細出力を要求し、修正してから再実行する
4. WARN は対処を検討し、許容する場合は理由を非公開の場所（コミットメッセージ等）に記録する（公開対象の検査記録.md に検出内容を転記しない — 二次漏洩の防止）
5. INFO は対処不要（整備推奨の通知のみ）

完了条件: Step 5-1 で固有名 0 件、かつ Step 5-2 で CRITICAL 0 件

### Phase 6: 公開（明示承認後のみ）

Phase 6 は、ユーザーがこのリポジトリの変更について「pushして公開」「公開してよい」など、公開を明示的に承認した場合だけ実行する。改善承認、ローカル検証完了、公開可否レビュー合格、ユーザーへの提示は公開承認の代わりにならない。

公開承認がない場合は Phase 5 で停止し、commit・push・PR作成・mainへのマージ・GitHub Pages確認を行わない。

このスキルの責務は `ai-slide-library` リポジトリ内の登録・公開工程に限る。グローバルスキル、グローバルルール、hook、ユーザー設定は変更しない。これらの変更が必要に見える場合は、このスキルの対象外として停止し、ユーザーへ確認する。

1. スライドHTML・サムネイル・検査記録・蓄積簿を commit（命名規約に従う）する
2. **コミット後に `node scripts/build-catalog.mjs` を再実行する**。スライドフォルダの `git log` から `updated`（表示日）と `updatedAt`（ソート用ISO日時）を取得し、対象スライドへ入っていることを確認する
3. 再生成された `index.html` を追加 commit する。カタログをコミット前に生成した場合は更新日時が欠落するため、この追加commitを省略してはならない
4. push → PR 作成 → main へマージする
5. 本番の `SLIDES` データを `updatedAt` 降順で確認し、対象スライドが意図した位置（最新なら先頭）にあることを確認する。同日更新を `updated` の日付だけで判定しない
6. 個別HTML・サムネイル・一覧のHTTPステータスと、一覧先頭の実表示を本番で確認する
7. worktree を片付け、メインツリーを最新化する

完了条件: 公開カタログの更新が確認され、worktree が残っていないこと

## ループ設計

| 要素 | 内容 |
|---|---|
| 反復条件 | Phase 4 のビルド停止（語彙外タグ・スライド実体不在・蓄積簿未登録フォルダ）を修正して再実行する ／ Phase 5: CRITICAL または固有名が検出されたら修正して Step 5-1 から再実行する |
| 上限回数 | Phase 4: 3 回 ／ Phase 5: 3 回 |
| 停止条件 | 収束停止: ビルド成功 ／ リソース上限: 3 回到達 ／ 発散検知: 同一エラーが 2 回連続 |

上限・発散で停止した場合は残エラーと原因を報告し、ユーザーの判断を仰ぐ。

## 重要な注意事項

- 公開リポジトリのため、特定顧客の情報・特定環境の絶対パスをスライド・蓄積簿・検査記録に入れない。Phase 5 の公開可否レビューで機械的に検査される。ただし reviewing-public-readiness 単独ではプロジェクト固有名の検出はできないため、Step 5-1 のスライド固有チェックが必須
- index.html のデータ部（CATALOG-DATA マーカー間）を手編集しない。変更は必ず蓄積簿 → 再生成の経路で行う
- 語彙一覧の語の削除・改名は既存スライドの再タグ付けを伴うため、スライド追加のついでに行わない

## 予想を裏切る挙動

- 共通スキルの蓄積簿登録（旧5列・リンク列あり）をそのまま使うと本リポジトリの11列形式と不整合になる。Phase 3 で必ず置き換える
- 該当スライドが0枚の語も、語彙一覧に登録するだけでカタログにグレーの選択不可チップとして表示される（準備中の見せ方としてこれが正）
- 語彙外タグでビルドが exit 1 で止まるのは意図した動作（表記ゆれの機械防止）。エラーを回避するために検査を外さない
