# repo-exportスライド取り込み（importing-repo-export-slides）

ダウンロードフォルダに生成される「repo-export」「repo-export 2」のようなエクスポートフォルダから、新デザインのHTMLスライドを本リポジトリへ取り込む前段処理を担う。対象確定・差分判定・共有CSS判断・機械的補正までを完結させる。完了後はルートB・Cを`adding-catalog-slides`へ、ルートDを`registering-html-slide-template`へ引き継ぐ。本スキル自身は`slides/`への最終登録・commit・pushを行わない。

## 使用タイミング

- ダウンロードフォルダのrepo-export系フォルダから新デザインのHTMLスライドを取り込む時
- 複数バージョンのexportフォルダ（番号違い）が存在し、対象の絞り込みが必要な時

## 前提

- `ls ~/Downloads`がsandbox制限で`Operation not permitted`になる場合がある。その場合はFinder経由で複製する。複製コマンドは次を使う。

```bash
osascript -e 'tell application "Finder" to duplicate folder ((path to downloads folder as text) & "repo-export N") to POSIX file "$CLAUDE_JOB_DIR/tmp" with replacing'
```

- まず直接アクセス（`ls -la $HOME/Downloads/...`）を試し、失敗した場合のみFinder経由に切り替える
- 元のダウンロードフォルダは変更しない（複製先で作業する）
- 同梱の`導入手順.md`は内容が古い場合がある。実際のフォルダ構成を正とする

## 補正3点の定義

本スキルは次の3点を「補正」と呼ぶ。この3点セットはPhase 1の「補正済みか」の判定とPhase 3の補正実行の両方で使い、片方だけを増減させない。

1. 共有CSSタグの位置が正しい状態を指す。`<link rel="stylesheet" data-shared-slide-shell>`が独自`<style>`の`</style>`の直後にある。`<script defer data-shared-slide-shell-script>`がその直後・`</head>`の直前に、この順序で続く
2. `<style>`内に`.slide`のpaddingの直接指定がない
3. `<title>`に「（新デザイン）」等の作業中を示す文言が残っていない

## 事前確認: パッケージ性質の判定

完了条件: パッケージ性質が判定され、体系更新の場合は扱い方針がユーザーと合意されていること

exportフォルダの同梱物から、パッケージ全体の性質を先に1回だけ判定する。

| 同梱物 | 判定 |
|---|---|
| `references/slide-design-system.md` または `assets/shared-slide-shell.css` の少なくとも一方を含む | デザイン体系の更新パッケージ |
| 上記の体系資産を含まない（スライドHTML等のみ） | 個別登録パッケージ |

デザイン体系の更新パッケージと判定した場合、キー別の処理へ入る前に`AskUserQuestion`でユーザーに確認する。確認内容は「体系更新として扱うか（共通シェル・デザイン仕様の更新可否を先に1回だけ判断）、スライド個別の取り込みとして扱うか」とする。個別と決まった場合はそのままPhase 1へ進み、共有CSS・デザイン仕様の扱いは既存のPhase 2（3条件チェック）に委ねる。

体系更新として扱うと決まった場合、共有CSS・デザイン仕様の更新可否を先に確定する。更新自体は定義（グローバルスキルと`assets/`の公開定義）の管理作業であり本スキルの対象外のため、方針確定後にスライドの取り込みへ戻り、その決定を前提としてPhase 1へ進む。

**完了**: パッケージ性質が判定され、体系更新の場合は扱い方針がユーザーと合意されている

## Phase 1: 対象確定と既存カタログとの突合

完了条件: 対象exportフォルダが1つに絞り込まれ、全キーがルートA（実質同一）／B（差し替え）／C（新規追加）／D（新型候補）／E（既存維持）のいずれかに振り分けられていること

Phase 1着手前に`git status --porcelain -- slides/`を確認する。未コミットの変更が残っている場合、前回実行の中断残骸である可能性がある。その内容をユーザーへ提示し、再開するか破棄するかを諮ってから進める。

## Step 1-1: 複数exportフォルダの包含関係確認

番号違いのexportフォルダが複数存在する場合、`Bash`で各フォルダの`slides/`配下のフォルダ名（キー）集合を列挙し、包含関係（一方が他方の完全なスーパーセットか）を確認する。最大集合を持つフォルダのみを以降の対象にする。例: `ls "$CLAUDE_JOB_DIR/tmp/repo-export 2/slides"`でキー集合を確認する。

exportフォルダが1つしか存在しない場合は包含関係の確認を省略し、そのフォルダをそのまま対象として確定する。包含関係になく互いに固有キーを持つ場合は最大集合が定まらないため、各フォルダのキー一覧を添えて`AskUserQuestion`でどちらを対象にするかユーザーに諮る。

**完了**: 対象exportフォルダが1つに絞り込まれている

## Step 1-2: 既存カタログとの機械的突合

既存`slides/`配下の全フォルダ名一覧と、対象フォルダのフォルダ名一覧を、Unicode正規化（NFC）を通してから比較する。`comm`はロケール・正規化形式（NFC/NFD）の差で誤判定するため、`Bash`からNode.js等で`String.normalize("NFC")`してから完全一致判定する。

```bash
node -e '
const fs=require("fs"); const n=s=>s.normalize("NFC");
const dirs=p=>fs.readdirSync(p,{withFileTypes:true}).filter(d=>d.isDirectory()).map(d=>n(d.name));
const a=dirs("<既存slides/パス>");
const b=dirs("<対象exportのslides/パス>");
const A=new Set(a);
console.log("既存にもある: "); b.filter(x=>A.has(x)).forEach(x=>console.log(x));
console.log("existing側に無い(新規候補): "); b.filter(x=>!A.has(x)).forEach(x=>console.log(x));
'
```

**完了**: 全キーについて既存カタログとの一致・不一致が機械的に判定されている

## Step 1-3: 本文照合によるルート振り分け

キー一致判定だけで取り込み可否を決めてはならない。既存にキーがある全件について、必ず本文を照合する。

```bash
diff "slides/<キー>/解説スライド.html" "<export>/slides/<キー>/解説スライド-新デザイン.html"
```

export側のファイル名は実際の構成を`ls`で確認して合わせる。`解説スライド-新デザイン.html`は2026-07-30時点の実構成の例示である。スライドフォルダ内に単一のHTMLがあればそれを照合対象とする。

差分の性質でルートを確定する。

| ルート | 条件 | 後続 | 検査深度 | 目安時間 |
|---|---|---|---|---|
| A: 実質同一 | 差分が`<title>`文言・共有CSSタグ位置・padding直接指定・用語統一レベルの軽微差のみ | 何もしない（判定記録のみ） | なし | 0分 |
| B: 差し替え | 本文・CSS実装・ページ構造に実質差分（デザイン体系コメントの有無も判断材料） | 補正 → 1スライド=1担当者で並列レビュー → adding-catalog-slides | 対象スライドのみフル検査記録8ファイル（hookがstaged HTMLに一律要求するため、Cと同じ深さ。差はスライド件数のみ） | 件数×5分+固定10分 |
| C: 新規追加 | 既存にキーなし、近似名があっても本文不一致 | adding-catalog-slidesへ直行 | フル検査記録8ファイル | 1件10分 |
| D: 新型候補 | 記入用テンプレート等、再利用される型の性質を持つ | AskUserQuestionで確認のうえregistering-html-slide-template | フル + 型選択ロジックの同期 | 30〜60分 |
| E: 既存維持 | 実質差分はあるが、incoming が更新版である根拠を示せない・既存版のほうが新しい・別テーマの資料・ユーザーが取り込まないと決めた | 何もしない（判定記録のみ） | なし | 0分 |

- ルートDはB・Cと排他ではない。まずキー有無と本文diffでB・C・Eを判定し、B・Cに該当したキーのうち再利用される型の性質を持つものをAskUserQuestionで確認のうえDへ振り直す
- 既存側が補正3点を満たしているかは「既存が登録フローを通過したか」の確認であり、incomingが新デザイン版かの判定には使えない。取り込み可否の判定基準にしてはならない（2026-07-30に5件の誤判定を実測）
- 近似名キー（表記揺れ・接尾辞違い）は本文照合で同一/別物を確定する。prh辞書適用後の名前が既存側に付いている場合がある
- 既存にキー・近似名がなくても、`docs/スライド主題一覧.md`の主題と突合する。類似主題の既存スライドがあれば本文を比較する。内容が既存の部分集合、または既存の統合元である場合はルートEとする。判断がつかない場合はユーザーに諮る（2026-07-30実測: 統合版が既存にある部品2件が別名のため新規候補と誤判定された）
- diff は差分の有無しか示さず、新旧の方向は判定できない。実質差分があっても、既存版のほうが新しい場合や別テーマの資料である場合がある。そのため、ルートB確定には「incoming が更新版である根拠」（デザイン体系コメントの有無や内容の包含関係等）を添える。根拠を示せない場合は機械的にBへ落とさず、差分の要約を添えてユーザーに諮る（2026-07-30 実測: 別テーマの資料をルートB相当と誤って差し替え扱いしかけ、レビューの fail で発覚した）。諮った結果、取り込まないと決まったキーはルートEとする

**完了**: 全キーがルートA／B／C／D／Eのいずれかに振り分けられている

## Phase 2: 共有CSS・デザイン仕様の取り込み判断

完了条件: 共有CSS・デザイン仕様を取り込むか否かが確定していること（既定は不取り込み）

## Step 2-1: 3条件チェック

同梱の`assets/shared-slide-shell.css`と`references/slide-design-system.md`は、公開中のものより古い可能性が高い。`Read`で同梱ファイルを読み、次のいずれかに該当すれば取り込まない（既定は不取り込み）。

- Google Fontsの`@import`が含まれる
- `Shippori Mincho`が含まれる
- `.slide`のpaddingが公開中の値と異なる（現行値は都度`Read`で`assets/shared-slide-shell.css`を実測して確認する。ハードコードした数値を鵜呑みにしない）

同梱されていないファイルは評価対象外として扱い、不在である旨を記録してPhase 4の提示に含める。

**完了**: 3条件のそれぞれについて該当・非該当が記録されている（対象ファイルが不在の場合は不在の記録をもって完了とする）

## Step 2-2: 判断がつかない場合

上記3条件のいずれにも該当しないが差分がある場合、`AskUserQuestion`で差分をユーザーに提示し、取り込む／取り込まないを選ばせる。差分がコメント行のみであっても既定の不取り込みへ短絡させず、必ずユーザーに諮る。

**完了**: 共有CSS・デザイン仕様の取り込み可否が確定している

## Phase 3: 取り込み対象の機械的補正

完了条件: ルートB・C・D確定分の全HTMLが、補正3点をすべて満たしていること

補正対象ファイル一覧と補正3点の変更内容は、Step 4-1の承認提示に含めて確認を得る。プランモードは使わない。補正対象が0件の場合はその旨をPhase 4の提示に含める。

## Step 3-1: 共有CSSタグの位置補正

同梱スライドは共有CSSタグの位置が崩れている場合がある。`<link rel="stylesheet" data-shared-slide-shell>`が独自`<style>`より前（7行目付近）にある。`<script defer data-shared-slide-shell-script>`も同様にその前にあるケースがそれである。これを`Edit`で`</style>`の直後・`</head>`の直前へ、同じ順序で移動する。正しい形の見本は既存の登録済みスライドを`Read`で参照する（例: `slides/レビューエンジン-3層構成/解説スライド.html`）。

**完了**: 対象HTML全件で共有CSSタグが`</style>`の直後・`</head>`の直前に並んでいる

## Step 3-2: padding直接指定の削除

`<style>`内に`.slide{ padding: ... }`の直接記述があれば`Edit`で削除する（共有CSS側の値に委ねる）。

**完了**: 対象HTML全件に`.slide`のpadding直接指定が残っていない

## Step 3-3: titleの確認

`<title>`に「（新デザイン）」「（新デザイン v2）」等の作業中を示す文言が残っていないか`Bash`で全件確認し、`Edit`で除去する。同一シリーズの複数スライドは`<ツール名>｜<共通の名前>`の形で統一されているか確認する。タイトルが40字を超え実描画ではみ出す場合、文言を勝手に決めず`AskUserQuestion`で候補を提示してユーザーに選んでもらう。

**完了**: 対象HTML全件のtitleに作業中を示す文言が残っておらず、シリーズ内の表記が統一されている

## Phase 4: 承認とフロー引き継ぎ

完了条件: 承認済みの対象が`slides/`へ配置され、ルートに応じた引き継ぎ先スキルが起動されていること（登録対象が0件の場合は0件である旨の報告をもって完了とする）

## Step 4-1: 分類結果の提示と承認

Phase 1〜3の結果（ルートA〜Eの各キー一覧、共有CSS取り込み可否、補正件数）を`AskUserQuestion`でユーザーへ提示し承認を得る。

- 削除相当の判断（ルートBによる既存ファイルの置き換え）は1件ずつ挙げて承認を得る。「まとめて整理」「不要と思われる」で削除しない
- 承認の解釈が曖昧なときはその解釈を明示して確認し直す
- 削除・置き換え前に必ず`Bash`で`git diff --cached --name-status | awk '$1=="D"'`を実行し、消えるファイルを全件確認して承認を得る。置き換え対象が0件の場合、または対象がgit管理下にない場合はこの確認を省略する
- ルートB・C・Dへ確定したキーは、Phase 3の補正3点を当該HTMLに適用してからStep 4-2の配置へ進む。Phase 3が先に完了していても、確定した時点で補正する

**完了**: ルートA〜Eの全件についてユーザーの承認が得られている

## Step 4-2: 後続フローへの引き継ぎ

承認後、補正済みHTMLを`Write`で`slides/<キー>/`へ配置する。ルートB・Cの引き継ぎ先`adding-catalog-slides`では、変更分類・機械検証・AIレビュー・ユーザー承認・登録・カタログ再生成・commit・pushを行う。これらは同スキルのPhase A〜Gで完結させる。ルートDの引き継ぎ先`registering-html-slide-template`は独自のPhase構成を持つため、同スキルの手順に従う。本スキルはいずれの経路でも登録・公開を代行しない。

登録対象（ルートB・C・D）が0件の場合は配置・起動のいずれも行わず、「登録対象0件」であることとルート別内訳を報告して終える。

**完了**: 承認済み対象が`slides/`へ配置され、ルートに応じた引き継ぎ先スキルが起動されている（登録対象0件の場合は0件である旨を報告済みである）

## 定型運用（時間予算と進行様式）

本スキルと`adding-catalog-slides`の連結実行は定型作業である。計画成果物を別途作らず、本スキル自体を手順書として扱う。

- プランモードを使わず、意思決定は各Stepの`AskUserQuestion`で都度行う。主要な承認点はパッケージ性質判定時の方針確認とStep 4-1の一括承認である
- 進捗報告は1行とする（例:「Step 1-3完了、ルートB 4件・E 1件。次はPhase 2」）。中間報告に表や長文を使わない
- 検査記録のAIレビューは1スライド=1担当者で並列に委任する
- PR作成前の敵対的検証はdiffへ1回を基本とする。採用修正が出た場合の再検証は妨げない
- 3ファイル以上の編集に入る前に`orchestrating-dev-flow`（設定・ドキュメント編集ルート）を起動してrouteを確定する。このskill-log記録が計画系スキルの実行記録となり、一括編集前計画ゲートを通過できる
- 時間予算: 取り込み判定は5分以内、実行時間はルート表の目安時間に従う（B: 1件5分＋固定10分、C: 1件10分）。7件規模の全体は30分以内を目標とし、超える見込みが立った時点で原因と見直し案を報告する。検査は1スライド=1担当者の並列実行のため、壁時計時間は直列合算ではなく最長1件分＋固定分で見積もる

## 予想を裏切る挙動

- 複数exportフォルダは包含関係にあることが多い。番号が大きいフォルダが必ずしも対象の全てとは限らないため、包含関係を機械的に確認してから最大集合のみを扱う
- exportフォルダの内容が新しく見えても、実際には既存版のほうが新しい場合はある。ただしその判定は本文照合（diff）で行い、既存側が補正3点を満たしているかを根拠にしてはならない（2026-07-30に5件の誤判定を実測）
- 共有CSS・デザイン仕様は複製せず、既存定義を参照するだけで良い。取り込み条件に反する場合は無条件に不採用とする
- 全キーがルートA（実質同一）またはE（既存維持）で登録対象が0件になる結末は正常な結果である。無理に新規追加を作らず、0件のまま報告して終える
- 検査記録のAIレビューは1件約4分かかる。複数件を1担当者に直列で渡さず、1スライド=1担当者で並列に委任する（2026-07-30実測: 3+4件の2分割直列で32分。7並列なら5分）
- exportの同梱物に体系更新の証拠（デザイン仕様・共有CSS・導入手順）が揃っている場合、個々のスライドの新旧判定より先にパッケージの性質を判定する。個別スライドとして処理すると、体系レベルの判断（共通シェルをどうするか）がキーごとに分散して矛盾する
