AI駆動開発セットアップ｜リバース工程・全体像（1/11）

流れは第一フェーズと第二フェーズに分かれる

第一はAIが読んで地図を作り、第二は地図を実行して設計書を作る。人の判断は3回。

第一フェーズ
役割 対象コードをAIが読み、第二フェーズが使う検出条件と、要件定義書・共通設計文書を作る
入力 対象コード（コミットを固定）
出力 道標（検出条件を含む）、要件定義書、共通設計文書6つ、承認用の要約1枚
人の判断 範囲の承認（1回）
→ 承認された道標
第二フェーズ
役割 道標の検出条件を実行して単位を実測し、単位ごとの基本設計・詳細設計・確認事項一覧を作る
入力 道標・要件定義書・共通設計文書・対象コード
出力 一覧、基本設計書、詳細設計書、確認事項一覧
人の判断 確認事項の提示、完了の受け入れ（2回）

既製の検索パターンは使わない。知らないリポジトリをAIが読み、その対象に合った検出条件を組む。

AI駆動開発セットアップ｜リバース工程・第一フェーズの全体（2/11）

第一フェーズは「読む→書く→閉じる」の3段で進む

6工程を3つの段にまとめる。大きな対象は領域に切って段階的に読み、承認で閉じる。

読む1-1・1-2
何をする フォルダ構成から読む領域と除外を決め、領域を1つずつ読んで検出条件と候補数を書く
出力 道標（対象・領域・除外・単位の見つけ方・候補数・到達範囲）
書く1-3・1-4
何をする 道標と文書から現状の要件を確定し、共通方式の実装を読んで共通設計文書を書く
出力 要件定義書（6節）、共通設計文書6つ
閉じる1-5・1-6
何をする 機械検査と自己レビューで直し、要約1枚を提示して範囲・除外・到達範囲の承認を得る
出力 検査の記録、承認用の要約1枚、承認の記録（人の判断1回）

人に聞くのは最後の承認1回だけ。中間で人を待たず、機械検査と自己レビューで前へ進める。

AI駆動開発セットアップ｜リバース工程・第一フェーズ 読む段（3/11）

読む段は、領域に切って道標を書く

1-1〜1-2。大きな対象は一度に読まず、領域を1つずつ読んで道標を育てる。

1-1 領域の切り出しと除外

フォルダ構成を読み、読む領域と読まない領域（生成物・依存・テスト等）を決める。ここで対象のコミットを固定する

出力道標の節0〜3（対象と時点・調査・領域・除外）

→
1-2 領域ごとの調査

領域を1つずつ読み、種別ごとの単位の見つけ方（検出条件）と候補数を書く。全領域を読み終えるまで繰り返す

出力道標の節4・6・9（単位の見つけ方・候補数・到達範囲）と節10（読みの記録）

既製の検索パターンは当てない。知らないリポジトリをAIが読み、その対象に合った検出条件を組む。

AI駆動開発セットアップ｜リバース工程・第一フェーズ 書く・閉じる段（4/11）

書く・閉じる段は、要件と共通設計を起こし承認で閉じる

1-3〜1-6。道標を根拠に文書を書き、機械検査で直し、要約1枚で承認を得る。

1-3 要件定義書

道標と文書から現状の要件を確定して書く

出力要件定義書（6節）

→
1-4 共通設計文書

共通方式の実装を読んで書く

出力業務仕様・方式・データ・エラー・共通外部仕様・基盤の6文書

→
1-5 検査と出し直し

機械検査と自己レビューで直す。同じ不合格が2回続いたら方法を変える

出力検査の記録、承認用の要約1枚

→
1-6 範囲の承認人

要約を提示し、範囲・除外・到達範囲の承認を得る

出力承認の記録

承認で否なら、理由の指す工程へ戻す。回数では止めず、同じ不合格が2回続いたら方法を変える。

AI駆動開発セットアップ｜リバース工程・道標の構造（5/11）

道標には、第二フェーズが実行する検出条件が入る

道標は11節。要の節は「単位の見つけ方」で、種別ごとに実行できる形の条件を持つ。

0対象と時点
1調査
2領域
3除外
4単位の見つけ方（検出条件・取り出しの規則）要の節
5動的な定義
6候補数
7共通方式の場所
8用語の候補
9到達範囲
10読みの記録
検出条件の例（画面） 
{ "種別": "screen",
  "単位の定義": "経路に対応するページを1つと数える",
  "走査": { "含む": ["frontend/src/pages"],
            "除く": ["**/*.test.tsx"], "拡張子": [".tsx"] },
  "一致": [{ "対象": "内容", "正規表現": "<Header title=" }],
  "分割": "ファイル",
  "名前": { "元": "内容", "正規表現": "title=\"([^\"]+)\"" },
  "例": ["frontend/src/pages/CharacterListPage.tsx"] }

第二フェーズの実行器は、この条件を解釈するだけで言語別の分岐を持たない。

AI駆動開発セットアップ｜リバース工程・第二フェーズの全体（6/11）

第二フェーズは、基本設計を全単位で閉じてから詳細設計へ進む

2-1〜2-13。前半で基本設計を閉じ、門を通ってから後半で詳細設計から受け入れまで進む。

前半2-1〜2-6
何をする 検出条件を実行して単位を実測し、事実を固定し、基本設計を書いて完了判定で閉じる
出力 一覧と元データ、機能と単位の対応表、技術スタック・環境構築手順書、単位ごとの事実、基本設計書、合格の記録
人の判断 無し
→ 保留を除く全単位と共通設計文書が合格するまで、後半へ進まない
後半2-7〜2-13
何をする 共通処理の詳細設計から単位の詳細設計へ進み、規約提案と確認事項をまとめ、提示と受け入れで完了する
出力 共通処理の詳細設計書、詳細設計書、規約提案、確認事項一覧、完了報告、納品物一覧
人の判断 確認事項の提示、完了の受け入れ（2回）

詳細設計へ進む判定は人に聞かない。機械検査と自己レビューの繰り返しで判定し、hookで止める。テスト設計（2-9）はいまのリバースではスコープ外。

AI駆動開発セットアップ｜リバース工程・第二フェーズ前半 実測（7/11）

前半は、検出条件を実測して事実を固定する

2-1〜2-4。道標を地図にして単位を数え、要件と突き合わせ、単位ごとの事実を取り出す。

2-1 一覧化

検出条件を実行して単位を実測し、候補数と突き合わせる

出力一覧と元データ

→
2-2 要件定義書の裏付け

機能要件と一覧を突き合わせる

出力機能と単位の対応表

→
2-3 基盤文書

依存の定義から書く

出力技術スタック、環境構築手順書

→
2-4 単位の事実の取り出し

取り出しの規則を実行して事実を固定する。機械で埋まる項目とAIが埋める項目を分ける

出力単位ごとの事実

一覧化で実測が候補数と2割を超えて食い違えば、道標の当該領域へ戻して再承認を受ける。

AI駆動開発セットアップ｜リバース工程・第二フェーズ前半 基本設計（8/11）

前半の終わりで、基本設計を書いて完了判定で閉じる

2-5〜2-6。事実を業務の言葉に写し、完了状態の観点を機械検査して合格の記録を残す。

2-5 単位の基本設計

事実を業務の言葉に写す。共通設計文書・要件定義書の受入条件・業務の言葉の決まりを参照する

出力基本設計書

→
2-6 基本設計の完了判定

完了状態の観点を機械検査し、合格の記録を書く。不合格は単位の基本設計へ戻す

出力合格の記録（共通設計文書を含む）

門 保留を除く全単位と共通設計文書の合格の記録が揃うまで、後半へ進まない

不合格の原因が共通設計文書なら、共通設計文書の再承認へ戻す。方法を変えても解決しない単位は保留にする。

AI駆動開発セットアップ｜リバース工程・第二フェーズ後半 詳細設計（9/11）

後半は、詳細設計を共通から単位へ書き、提案と確認事項を出す

2-7〜2-11。共通処理を先に書き、コードと1対1の詳細設計へ進む。

2-7 共通処理の詳細設計

基盤層と共通部品を先に書く

出力共通処理の詳細設計書

→
2-8 単位の詳細設計

コードと1対1で書く。表はテーブル定義書にする

出力詳細設計書

→
2-10 規約提案

文書とコードから提案を出す。用語の追加候補を含む

出力規約提案

→
2-11 確認事項一覧

各工程の確認事項を1枚にまとめる

出力確認事項一覧

2-9 テスト設計はいまのリバースではスコープ外。番号は将来の拡張のために残す。

AI駆動開発セットアップ｜リバース工程・第二フェーズ後半 人の判断（10/11）

人に聞くのは提示と受け入れの2回で、完了する

2-12〜2-13。確認事項をまとめて提示し、完了報告と納品物一覧で受け入れを得る。

2-12 確認事項の提示人

確認事項一覧を提示し、回答を受ける。回答は設計書へ反映する

出力提示の記録

→
2-13 完了報告と受け入れ人

納品物一覧と完了報告を出し、受け入れを得る

出力完了報告、納品物一覧

中間で人を待たない。差し戻しは表で決め、回数では止めない。

AI駆動開発セットアップ｜リバース工程・決まりと差し戻し（11/11）

守る決まりは4つ。差し戻しは表で決め、人に聞くのは3回

決まりを崩さないために、戻り先と方法の変え方を表に固定する。

✓ 要件が先（要件定義を基本設計より先に置く）
✓ 基本設計を閉じる（全単位の基本設計を閉じてから詳細設計へ）
✓ 単体テスト設計書はスコープ外（いまのリバースでは作らない）
✓ 共通の詳細が先（共通処理の詳細設計を単位より先に書く）
どこで見つかるどこへ戻る
一覧化で実測が候補数と2割を超えて食い違う 道標の当該領域（再承認）
基本設計の完了判定で不合格 単位の基本設計
不合格の原因が共通設計文書 共通設計文書（再承認）
承認で否 理由の指す工程

回数では止めず、人にも戻さない。同じ不合格が2回続いたら方法を変え、方法が尽きたときだけ対象外かAIの読み取りに倒して進む。
