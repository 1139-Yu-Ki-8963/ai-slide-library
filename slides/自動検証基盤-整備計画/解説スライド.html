自動検証基盤 — テスト系

AI導入前に、成果物を機械で証明できる基盤を整える

テスト系5項目：現状 → 先に整える文書 → 次の行動を、1行で読む

やりたいこと 現状 必要なコンテキスト文書 次に行うこと
テスト
フレームワーク導入		 未導入フレームワーク未選定で自動テストが存在しない ツール選定言語・既存ビルド構成に合わせて選ぶ（JS: vitest / Jest　Ruby: RSpec　Python: pytest 等） 言語とビルド構成に合うフレームワークを選定し、導入する
単体テスト整備 未整備関数の入出力仕様が未定義で、テストを書く基準がない 観点表各関数の引数・戻り値・例外条件を一覧化する 観点表を整理 → 単体テストを実装
結合テスト整備 未整備モジュール間の接続仕様が暗黙知のままになっている API 設計書 / データフロー定義モジュール間のデータの流れ・形式・制約を定義する API 設計書を整備 → 結合テストを実装
E2E テスト整備 未整備画面操作の期待動作が口頭伝達で、再現性がない 画面設計書操作手順・画面遷移・期待表示を定義する 画面設計書を整備 → E2E テストを実装
カバレッジ計測導入 未導入テストの網羅率を把握する手段がない CI 設定の前提定義目標値・除外対象を定義する 目標値を決め、CI にカバレッジ計測を組み込む
結論 テストコードより先に、観点表と設計書 — 文書の整備が「機械で証明できる状態」への最短経路 1 / 2
自動検証基盤 — 静的検査系

AI導入前に、成果物を機械で証明できる基盤を整える

静的検査系4項目：規約の言語化 → 検査設定への変換を、行動順に読む

やりたいこと 現状 必要なコンテキスト文書 次に行うこと
コード linter 導入 未導入規約が暗黙知で、linter 設定の根拠がない コーディング規約rules/ に命名規則・禁止パターン・ファイル構成方針を定義する 規約を rules/ に文書化 → linter 設定へ変換
文体 linter 導入 未導入用語の表記揺れが放置され、読み手に負担がかかっている 文体規約 + 用語辞書文長・読点数・冗長表現等と用語辞書（prh.yml）を定義する 文体規約・用語辞書を整備 → textlint を導入
リンク切れ検査導入 未導入リンク切れの検知が目視頼みで見落としが発生する リンク検査設定検査対象のファイル範囲と除外パターンを定義する 検査範囲・除外条件を定義 → リンク検査を導入
HTML 静的検査導入 未導入HTML 品質検査の基準が未定義で、検査が実施できない 検査観点rules/ に必須属性・アクセシビリティ等の機械検査の観点を定義する 検査観点を rules/ に定義 → linter 設定へ変換
結論 規約の言語化が先、ツール導入が後 — linter の設定はすべて規約文書から導出する 2 / 2
