レビューエンジン 3層構成

第1層 — 機械的チェックが、人が見る前に指摘を消す

3種の自動検査を、この順に全対象へ流す

置き換え辞書

カタカナ語・英語バズワードを検出し、平易な日本語の推奨語へ置き換える。

アジェンダ → 議題 リソース → 資源 ナレッジ → 知見
→
textlint

文の長さ・読点の数・漢字連続など、読みやすさの定量基準を機械検査する。

1文 100字以内 読点 3個以内 漢字連続 7文字以内
→
略称照合

説明なしの略称・頭字語を検出し、初出時に正式名称の定義を強制する。

ref → 参照 SHA → ハッシュ値 初出時に正式名称を定義
効果 語彙・文体・略語の指摘は、人のレビューに届く前に消える 2 / 5
レビューエンジン 3層構成

第2層 — 対象が触るものが、適用する規約を決める

規約は人が選ばない。計画の領域と変更パスから自動で解決する

計画の提示前に発火 計画の領域から

計画文が何に触れるかを読み、その領域の設計基準を照合に加える。

計画文が UI に触れる→UI 実装基準 計画文が DB に触れる→DB 設計基準 計画文が API に触れる→API 設計基準 計画文が認証に触れる→セキュリティ基準
実装の完了後に発火 変更ファイルから

差分に含まれるパスの型を見て、その種類の実装基準を照合に加える。

*.html を変更→HTML 出力基準 src/components/ を変更→UI 実装基準 *.test.* を変更→テスト基準 schema.prisma を変更→DB 設計基準
例外 成果物の提示前では実行しない。共通基準のみで照合する 3 / 5
レビューエンジン 3層構成

第3層 — 判断系レビューは、責務の違う4人の専門家に分ける

名前が濃い専門家だけが、合否を宣言できる

文書照合SONNET合否を宣言する

文書成果物を規約に照合する。形式・構成・文節改行・意味キーの4観点。

コード照合SONNET合否を宣言する

コード差分を規約に照合する。共通基準とUI実装基準の2観点。

反証OPUS所見のみ

作成文脈を持たない懐疑者として「誤りがある」前提で証拠を探す。合否は宣言しない。

初見読解HAIKU所見のみ

初見で計画を読み、実行できるかを試す。読めなかった箇所が、省略された暗黙知の証拠。

合否宣言権 宣言できるのは文書照合とコード照合だけ。反証と初見読解は所見を返す 4 / 5
レビューエンジン 3層構成

対象ごとに、専門家の組み合わせを替える

計画・成果物・実装では、失敗の種類が違う

レビュー対象 組み合わせ ねらい
計画の提示前 文書照合 ＋ 3観点反証 ＋ 実行可能性の検証 暗黙知と論理の穴を、提示前に潰す
成果物の提示前 文書照合 ＋ HTML出力 ＋ 理解可能性の検証 表示品質と初見理解を、提示前に確認する
実装の完了後 コード照合 ＋ 差分反証 規約違反と破壊的差分を、完了後に探す
原則 失敗の種類が違えば、選ぶ専門家も違う 5 / 5
